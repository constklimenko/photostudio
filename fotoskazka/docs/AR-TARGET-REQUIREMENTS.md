# D1.1 — Практические требования к фотографии как Image Target

**Дата:** 2026-09-20
**Контекст:** продолжение подэтапа D1.1 roadmap «Собственный сервис „оживающих
фотографий“ (WebAR)». Развивает раздел 3.5 файла
`docs/AR-TECHNOLOGY-RESEARCH.md` (требования к качеству печатного маркера) и
отвечает на вопрос, вынесенный в приоритет: **можно ли использовать саму
напечатанную фотографию как Image Target без специальной переработки**.

**Статус:** исследовательский документ. Решения не принимает (принятие — на
контрольной точке D1.5). Никакой код, БД и архитектура не изменяются.
Данные собраны по документации и официальным источникам кандидатов из shortlist
D1.1 (MindAR, 8th Wall, AR.js) и общеприменимой практике image tracking.

**Нотация пометок:**
- `[ПОДТВ]` — подтверждено документацией/официальными материалами конкретной
  технологии (источник указан).
- `[ЭКСП]` — не подтверждено документацией; проверяется экспериментом на
  D1.2–D1.3 (по roadmap) и тестовой матрицей D1.9.
- `[ОБЩ]` — общий вывод, следующий из принципов работы feature-based trackers,
  справедливый для всех указанных движков с оговоркой, что численные пороги
  остаются `[ЭКСП]`.

---

## 0. Краткий итог

1. Фотоснимок — в целом **хороший класс target-изображений** для
   feature-based image tracking (примеры хороших targets в документации всех
   движков включают «группы людей», «коллажи», «уличные сцены»)
   `[ПОДТВ: MindAR, Vuforia]`. Принципиальной необходимости в специальном
   рисунке-маркере нет.
2. Однако **типовая школьная/детская фотография — один из худших по структуре
   кандидатов**: однотонный или градиентный фон, один центр-объект, крупные
   однотонные области, часто глянец и малый размер отпечатка. Каждая такая
   фотография требует индивидуальной проверки feature-точек.
3. Однозначный ответ «можно ли без переработки» для конкретной
   фотографии/печати даёт только эксперимент. Документация не даёт численных
   порогов для пар «SDK × печать × телефон» — это вынесено в `[ЭКСП]`.
4. **Рабочая гипотеза для D1.2–D1.3:** часть портретов сработает «как есть», но
   для стабильного прод-сценария большинству потребуется отдельная
   подготовка target-изображения (кадрирование, усиление контраста, добавление
   текстурированной окантовки) **и матовый отпечаток**.

## 1. Как работает Image Tracking (кратко)

- Трекер извлекает «feature points» (углы, края, перепады яркости) из
  **эталонного цифрового изображения** и сравнивает их с features в кадре
  камеры в реальном времени `[ОБЩ]`.
- MindAR: особенности извлекает компилятор Image Targets Compiler; результат —
  файл `targets.mind`; компилятор показывает найденные feature points
  (красные точки) — можно визуально оценить их количество и распределение
  ещё до распечатки `[ПОДТВ: hiukim.github.io/mind-ar-js-doc/tools/compile]`.
- AR.js: дескрипторы создаёт NFT Marker Creator (`.fset`, `.iset`, `.fset3`),
  движок — jsartoolkit5 (Natural Feature Tracking) `[ПОДТВ: ar-js-org.github.io/AR.js-Docs/image-tracking]`.
- 8th Wall: Image Target генерируется локально `npx @8thwall/image-target-cli`
  (в т.ч. luminance-изображение для сравнения с камерой) `[ПОДТВ: github.com/8thwall/8thwall, apps/image-target-cli]`.
- Общее следствие: **напечатанная фотография должна геометрически точно
  повторять цифровой файл, по которому собран target** — то же кадрирование,
  без дополнительных рамок/водяных знаков/искажений перспективы. Цвет может
  отличаться (движки работают с яркостью/интенсивностью, а не цветом `[ПОДТВ: MindAR]`),
  но геометрия — должна совпадать `[ОБЩ]`.

## 2. Какие визуальные особенности помогают tracking

| Свойство изображения | Почему помогает | Источник |
|---|---|---|
| Много деталей («complexity»: линии, грани, текстуры, пятна) | больше feature points, выше вероятность сопоставления | `[ПОДТВ: MindAR — «the more complex the image is, the better»]` |
| Чёткие углы и рёбра (корнер/edge detection) | MTF системы основан на резких перепадах яркости | `[ПОДТВ: MindAR; Vuforia]` |
| Высокий контраст (сильные перепады яркости) | контрастные области дают «сильные» features | `[ПОДТВ: MindAR, Vuforia, NRSDK]` |
| Равномерное распределение features по всему кадру, включая края | устойчивость к частичному перекрытию, надёжная ориентация | `[ПОДТВ: MindAR — правила распределения; Vuforia — равномерное распределение]` |
| Отсутствие повторяющихся и симметричных паттернов | разные points различимы, однозначная ориентация | `[ПОДТВ: MindAR, Vuforia]` |
| Высокая пространственная частота (мелкая текстура) | много различимых отдельных точек | `[ПОДТВ: jsartoolkit5/NFT constraints — high spatial frequency]` |
| Матовость и плоскостность печатного носителя | нет бликов, нет искажения геометрии | `[ПОДТВ: Vuforia, NRSDK; [ЭКСП] для MindAR/8th Wall]` |
| Статичность (не скрин, не дисплей) | экраны дают блики/мерцание и зависят от яркости | `[ОБЩ]` |

Правила MindAR (дословно по официальной серии «How to choose a good target
image», автор Hiu Kim Yuen — мейнтейнер MindAR):
1. изображение должно быть **сложнее** (больше точек, линий, форм);
2. избегать **повторяющихся и симметричных** паттернов (повторяющиеся точки
   путают сопоставление, симметрия запрещает определить ориентацию);
3. избегать **пустых областей**, особенно по периферии (должны быть features у
   краёв);
4. **контраст полезен**, цвет — почти не важен (движки переводят в grayscale,
   важна относительная яркость пикселей); градиентные переходы бесполезны
   («gradual changes mean no changes»);
5. разрешение важно слабо; «as a rule of thumb» достаточно ~1000 px по стороне
   `[ПОДТВ: mindar.org / Medium — серия автора]`.

## 3. Какие фотографии подходят плохо

- Большое однотонное/пустое поле (небо, стена, градиентный фон портретов).
- Размытый bokeh-фон, «мягкие» круглые формы без чётких граней.
- Слишком низкий/высокий контраст (пересвет, недодержка, «плоский» кадр).
- Текстуры, которые выглядят повторяющимися (кирпич, трава, волны, ткани с
  повторяющимся рисунком) — при большом повторе.
- Сильная симметрия (портрет анфас на симметричном фоне — одна из главных
  проблем школьных фото).
- Жёсткий JPEG-артефакт/пережатие, сильное шумоподавление, программное
  «размытие лица» (beauty-ретушь убирает края).
- Сильная компрессия и малый цифровой исходник, «рисованный» размытый фон.
- Однотонный фон студийного портрета + центр-анфас.
- Фото в широкой белой паспарту/рамке без деталей по краям.
- Любой снимок с большими зонами без деталей и без стабилизирующих features
  по краям.

## 4. Влияние контраста

- Высокий контраст прямо называют положительным фактором MindAR и Vuforia:
  углы и рёбра более заметны → больше качественных features
  `[ПОДТВ: MindAR, Vuforia]`.
- Движки работают с **относительной яркостью (grayscale)**, а не с цветом.
  Цветовая пере-преобразование в градации серого может терять детали —
  важны перепады **яркости**, а не «красивость» цвета
  `[ПОДТВ: MindAR; Vidinoti — «система работает на grayscale»]`.
- Плавные цвето-тональные градиенты (например, градиентный фон студии) не дают
  features: «only sharp changes matter» `[ПОДТВ: MindAR]`.
- Советы по усилению: локальный контраст, чёткие рёбра, светлый
  текстурированный фон вместо пустого `[ПОДТВ: Vuforia best practices]`.
- Для печати: печатная гамма сужает динамический диапазон (тиражная печать
  теряет крайние тени/света) → контраст отпечатка ниже, чем у цифрового
  оригинала, что может ухудшить сопоставление `[ОБЩ]`.

---

## 5. Повторяющиеся и симметричные элементы

- Повторяющиеся элементы (одинаковые лица, одинаковые фигуры, одинаковые окна,
  шахматная доска, трава, кирпич) дают **неразличимые** feature points и путают
  сопоставление; шахматная доска — отрицательный пример в официальных
  материалах `[ПОДТВ: MindAR, Vuforia]`.
- Вертикальная/горизонтальная симметрия мешает движку определить ориентацию:
  два зеркальных варианта почти равновероятны `[ПОДТВ: MindAR]`.
- Для групповых фотографий класса: ряды одинаковых лиц в одинаковой форме,
  выстроенные в линию — близко к паттерну «повторение», особенно при однотонном
  фоне `[ОБЩ]`. Есть риск, что такая фотография будет хуже трекаться, чем
  одиночный портрет с деталями одежды/причёски.

---

## 6. Крупные однотонные области

- Крупные однотонные области — главный «убийца» tracking: в них нет feature
  points, распределение точек становится неравномерным.
  `[ПОДТВ: jsartoolkit5/NFT constraints — «Images with large areas of single flat
  color ... will not track well, if at all»; MindAR — «avoid blank space»]`.
- Пустые области по периферии хуже, чем в центре: если по краям нет точек,
  теряется устойчивость и точность позиции `[ПОДТВ: MindAR]`.
- Лекарство (без смены самой картинки): кропнуть пустые поля, добавить
  текстурированную окантовку/фон (например, рамка из окружающей среды) —
  приём прямо рекомендован: «If the image is too plain, consider adding a
  background» `[ПОДТВ: MindAR]`.
- У студийных портретов фон занимает 40–60% площади → на нём нет features.
  `[ОБЩ]`

---

## 7. Глянцевая и матовая печать

- **Матовая поверхность предпочтительна**, глянец не рекомендуется — согласная
  рекомендация практически всех источников `[ПОДТВ: Vuforia; NRSDK; MindAR
  (не-отражающие материалы); [ЭКСП] для прямого сравнения MindAR/AR.js/8th Wall]`.
- Глянцевый отпечаток под определённым углом даёт **зеркальный блик от
  источника света** (лампа, окно, солнце), который «накрывает» часть текстуры и
  работает как частичное перекрытие target — тогда features пропадают
  `[ПОДТВ: Vuforia physical properties; Carnaux NFT Creator wiki — «strong lights
  cause reflections that can make your marker appear white»]`.
- Лазерная печать и фотовывод — часто сильно глянцевые `[ПОДТВ: Vuforia]`.
- Школьные фотографии и фотоальбомы обычно печатаются на глянцевой
  фотобумаге → повышенный риск бликов (`[ЭКСП]` насколько критично).
- Mitigation: лампинация/матовое ламинирование поверхности, плотная (или
  текстурированная) фотобумага, съёмка под углом, не создающим блика `[ОБЩ]`.

## 8. Размер фотографии

### 8.1 Цифровое разрешение (исходник для компиляции target)

- MindAR: разрешение «обычно не критично», «rule of thumb» — сторона ≥1000 px;
  меньшее (≈100 px) явно плохо; избыточно высокое — не помогает больше
  (упирается в камеру/вычисления) `[ПОДТВ: MindAR]`.
- AR.js/jsartoolkit5: чем больше/выше разрешение исходника, тем лучше выделяются
  features при более высоких степенях и при близкой камере; поверхности с
  «reasonable fine detail and sharp edges» `[ПОДТВ: jsartoolkit5 NFT constraints]`.
  При этом веб-NFT-Marker-Creator «менее эффективен» для изображений
  ≥1000 px по стороне — инструментальное ограничение `[ПОДТВ: NFT-Marker-Creator]`.
- 8th Wall: явных численных требований к разрешению/размеру target-исходника в
  документации (сентябрь 2026) не обнаружено — `[ЭКСП]`.
- Изображения в МБ: Vuforia ограничивает 2.25 МБ и минимум 320 px — это про
  другой (нативный) стек и носит справочный характер `[ОБЩ, не наш стек]`.
- Общий вывод: использовать исходник с максимальным доступным разрешением
  исходника (оригинал, не превью), избегать пережатия; детали на мелких
  элементах (текстура одежды, волосы) должны оставаться читаемыми `[ОБЩ]`.

### 8.2 Физический размер отпечатка

- Формально документация не фиксирует минимальный физический размер для
  MindAR/AR.js/8th Wall `[ЭКСП]`.
- Общий принцип: **важна не дистанция сама по себе, а доля экрана, занимаемая
  target**, и наличие различимых features; target должен занимать значительную,
  предпочтительно центрированную часть кадра
  `[ПОДТВ: официальный форум 8th Wall]`.
- Справочно (другой стек): Vuforia для ближнего стола рекомендует отпечаток
  ≥5 дюймов (≈12 см) по ширине; правило «min size ≈ дистанция / 10»
  (источник — рекомендации Vuforia/Wawa) — для нашего стека `[ЭКСП]`, numerical
  принимается как гипотеза для проверки.
- Следствие для фотоальбома: разворот/страница 20×30 см и крупнее дают больше
  «полезной площади» на кадр камеры, чем фото 10×15 см `[ОБЩ]`.

## 9. Качество печати

- Отпечаток должен «походить» на исходник: «does the target captured in camera
  look alike the original image» — прямое требование MindAR `[ПОДТВ: MindAR]`.
- Плоскостность: тонкая бумага гнётся/волнами, искажая геометрию; рекомендованы
  жёсткие носители (картон, пластик, приклейка на жёсткую основу), плотная
  бумага 200–220 г/м² или монтаж на фоам/картон 3–5 мм `[ПОДТВ: Vuforia,
  ARLOOPA; [ЭКСП] на сколько критично для нашего стека]`.
- Полупрозрачная тонкая бумага просвечивает стол/подложку — меняет вид target
  `[ПОДТВ: Carnaux NFT Creator wiki]`.
- Цвет печати не обязан идеально совпадать (движок работает с яркостью), но
  геометрия, кроп, отсутствие наложений (водяных знаков, ламината с
  «голографией», жёсткого тиснения) обязательны `[ОБЩ]`.
- Артефакты печати: banding, сильное падение резкости, чернильные разводы —
  снижают качество сопоставления `[ОБЩ]`.
- Печать «1:1 по кропу» с тем же файлом, из которого собран target — обязательно
  (иначе геометрия не совпадёт) `[ОБЩ]`.

## 10. Освещение

- Требование-клише всех движков: ровное, умеренно яркое освещение без жёстких
  бликов `[ПОДТВ: MindAR (качество света), Vuforia (evenly lit diffused), NRSDK]`.
- Жёсткий боковой/контровой свет даёт тени и блики, «перекрывающие» features;
  низкий свет — шум кадра и мало контраста `[ОБЩ]`.
- Для глянца: освещение «ambient» без прямого источника, отражение которого
  попадает в объектив `[ПОДТВ: Vuforia]`.
- Численные пороги освещённости (лк) в документации MindAR/AR.js/8th Wall не
  обнаружены → `[ЭКСП]` (критерий D1.3: искусственный и дневной свет).

---

## 11. Расстояние до камеры

- Численных максимумов дистанции в документации нашего стека нет — `[ЭКСП]`.
- Решающим является **видимый размер target в кадре** (доля кадра по экрану) и
  разрешение камеры; большие target (например, стена дома) трекаются издалека,
  маленькие — только вблизи `[ПОДТВ: форум 8th Wall]`.
- Гипотеза для проверки: расстояние ≈ (5–15)× меньшей стороны отпечатка в
  зависимости от SDK/телефона `[ЭКСП]`.
- Для сценария «альбом в руках» типичная дистанция 20–40 см — насколько этого
  хватает для отпечатка 10×15 и 20×30 см: `[ЭКСП]`.

---

## 12. Угол наклона

- Формальных пределов наклона в документации MindAR/AR.js/8th Wall нет — `[ЭКСП]`.
- NRSDK (другой стек, справочно): быстрее всего инициализировать tracking под
  лёгким углом, держа поверхность плоской и неискажённой `[ОБЩ/справочно]`.
- Сильный угол => перспективные искажения ломают сопоставление с плоским
  эталоном; блик на глянце усиливается при наклоне к источнику света `[ОБЩ]`.
- Для D1.9 в roadmap заданы измерения «угол наклона» — пороги фиксируем
  экспериментально `[ЭКСП]`.

## 13. Проблемы с фотографиями детей / школьными портретами

Это отдельный раздел, потому что контент Фотосказки — прежде всего школьные и
детские портреты из выпускных альбомов.

| Проблема типового снимка | Риск для tracking |
|---|---|
| Однотонный/градиентный студийный фон (серый/белый/пастель) | большая пустая область без features; распределение точек неравномерно |
| Анфас, симметричный портрет | вертикальная симметрия мешает определить ориентацию |
| Центр-объект и большие поля по краям | нет features у периферии, нестабильная позиция |
| Beauty-ретушь, «размытие лица», мягкое боке | теряются рёбра/углы — те самые features |
| Пересвет кожи, белый фон, «high-key» | низкий контраст, мало перепадов в ключевых зонах |
| Маленький отпечаток 10×15 глянец | малый видимый размер в кадре + блики |
| Группа детей в одинаковой форме в ряд | повторяющиеся похожие фигуры/лица, низкая различимость |
| Пережатие WP-превью вместо оригинала | артефакты JPEG и потеря деталей в исходнике target |
| Кадрирование: «фото с принтера» обрезано/в паспарту не совпадает с файлом | геометрическое расхождение с эталоном |

Особый случай — **серия очень похожих фотографий (один альбом, один фон, один
ребёнок)**: features одной фотографии могут «походить» на features другой.
Risks: ложное срабатывание на «не свою» фотографию и соревнование соседних
target'ов (в контексте 8th Wall зафиксирован переход между двумя очень похожими
target'ами) `[ПОДТВ: форум 8th Wall — switching между похожими targets;
справочно]`. Следствие для архитектуры: **нужно ещё на этапе выбора
фотографий/Target-ов учитывать различимость target-изображений друг от друга**
`[ОБЩ]`. Численные пороги «различимости» — `[ЭКСП]`.

## 14. Нужна ли подготовка отдельного target-изображения (главный вопрос)

### Ответ

- **Да, можно использовать саму фотографию как target**, работающую напрямую,
  **только если** в ней достаточно качественных, различимых и равномерно
  распределённых feature points — и это **проверяется визуально в компиляторе
  до печати** (MindAR: красные точки; AR.js: дескрипторы/качество; в 8th Wall —
  через CLI-генерацию и тестовое распознавание) `[ПОДТВ: MindAR compiler]`.
- Для «богатых деталями» снимков (группа на улице, коллаж, интерьер,
  фоторепортаж) — прямое использование без переработки реально и ожидаемо
  `[ПОДТВ: MindAR/Vuforia — «group of people» в примерах хороших targets]`.
- Для типовых школьных/студийных портретов **вероятность, что понадобится
  переработка, высокая** из-за фона, симметрии, ретуши и глянца (раздел 13).
- **Правильный процесс:** сначала прогнать цифровой файл через компилятор/CLI
  целевого SDK → оценить число и распределение feature points → только затем
  печатать тот же файл и тестировать отпечаток. Если точек мало/неравномерно —
  **подготовить отдельный target-файл** (см. ниже) и пере-компилировать.
- Численного порога «достаточно точек» документация MindAR/AR.js не даёт —
  критерий «устойчиво удерживается в кадре» из roadmap D1.2 фиксируется
  экспериментально `[ЭКСП]`.

### Способы подготовки отдельного target без изменения самой фотографии

1. **Кропнуть пустые поля** (убрать паспарту/небо/фон) вокруг объекта — приём
   прямо рекомендован MindAR `[ПОДТВ: MindAR — «cropping the center»]`.
2. **Добавить текстурированную окантовку/фон** (книжный/альбомный задник,
   декоративная рамка, обложка альбома) — добавляет features по периферии
   `[ПОДТВ: MindAR — «adding a background»]`.
3. **Локальное повышение контраста/резкости рёбер** без визуального ущерба
   для фото `[ПОДТВ: Vuforia — local contrast enhancement]`.
4. **Отказаться от beauty-ретуш-версии как target**: для target использовать
   файл с деталями, а «красивая» версия остаётся в альбоме (если это допустимо
   по сценарию) `[ОБЩ]`.
5. **Печатать на матовом носителе / ламинировать матово** `[ПОДТВ: Vuforia,
   NRSDK]`.
6. **Правильный формат экспорта:** PNG/JPEG без пережатия, RGB (не CMYK, без
   альфа-канала) `[ПОДТВ: Vuforia (справочно); jsartoolkit5 — JPEG]`.

Важно: если переработанный файл стал target, **печатать надо именно его**
(или его «чистую» без-декора версию 1:1). Таргет и отпечаток — один и тот же
кадр. `[ОБЩ]`

## 16. Что проверить экспериментом на D1.2–D1.3 (минимальный набор)

По roadmap D1.3: «зафиксированы предельные параметры качества печати». Для
этого на экспериментальных стендах измерить:

1. Один и тот же отпечаток в диапазоне физических размеров (10×15, 15×20,
   20×30, страница альбома ≥ 20×30 см). Критерий: % попыток с устойчивым
   tracking ≥ нескольких секунд (по D1.2).
2. Матовый vs глянцевый вариант одного снимка при одинаковом свете.
3. Искусственный свет vs дневной свет; блик от лампы/окна.
4. Дистанцию от 15 см до 1.5 м с шагом; по каждому SDK (MindAR, 8th Wall,
   AR.js) и обоим телефонам.
5. Наклон 0°, 15°, 30°, 45° по осям.
6. Специфические снимки Фотосказки: одиночный студийный портрет,
   групповой классный снимок, фото в альбоме (страница в обороте), коллаж.
7. Проверить визуально количество feature points в компиляторе MindAR и
   соотнести с успешностью — попытаться зафиксировать рабочее «много/плохо»
   правило для внутренних use.
8. Различимость двух похожих портретов одного альбома (серия targets).
9. Версия с подготовленной окантовкой/кропом против «как есть» — количественно.

Результаты — в отчёт D1.2 (первый прототип) и таблицу D1.9, после чего
пороги параметров можно фиксировать как подтверждённые.
