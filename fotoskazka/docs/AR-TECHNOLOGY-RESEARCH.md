# D1.1 — Исследование технологий WebAR / Image Tracking

**Дата:** 2026-09-20
**Контекст:** подэтап D1.1 roadmap «Собственный сервис „оживающих фотографий“ (WebAR)».
Сценарий: пользователь наводит камеру смартфона на напечатанную фотографию → система распознаёт изображение → поверх фотографии воспроизводится связанное видео.

**Статус:** исследовательский документ. Решения не принимает (принятие — на контрольной точке D1.5). Данные собраны по официальным источникам и GitHub по состоянию на сентябрь 2026.

## 1. Подтверждённые факты

### 1.1. Общие факты для любого браузерного AR

- Доступ к камере в мобильном браузере требует **HTTPS** (secure context) и `getUserMedia` (WebRTC). Без HTTPS камера недоступна.
- Браузерный AR без приложения принципиально реализуем: все ниженазванные движки (кроме чистого WebXR) обрабатывают кадр камеры сами (WebRTC + WebGL/WebAssembly), поэтому работают в обычном мобильном браузере.
- Image Tracking требует качественного маркера: **контрастность, детализация, отсутствие повторяющихся паттернов, отсутствие бликов**. Глянцевая печать и неровное освещение снижают распознавание (официальные рекомендации всех SDK сходятся в этом).
- **iOS Safari не поддерживает WebXR** (`immersive-ar`) — ни на iPhone, ни на iPad, ни на macOS. Подтверждено W3C/разработчиками Apple и независимыми источниками 2026 года (см. 1.4). Это главное ограничение «чистого стандарта».
- **Android Chrome поддерживает WebXR AR нативно**, но модуль Image Tracking (WebXR Marker Tracking) — только под флагом `chrome://flags/#webxr-incubations`.
- Автовоспроизведение видео с операционной системой: на **iOS без пользовательского жеста видео с дорожкой звука не автостартует**; требуется `muted` + `playsInline` (+ при необходимости жест для звука). Android (Chrome) в целом мягче, но приложения-встроенные вебвью (Instagram, VK, Facebook) часто блокируют/ограничивают камеру — в них AR некорректно работает (нужно открытие в обычном браузере).

### 1.2. MindAR (github.com/hiukim/mind-ar-js)

- Open-source WebAR SDK (Image Tracking + Face Tracking). **MIT**, бесплатен, включая коммерческое использование.
- Image Target создаётся в **браузерном компиляторе** (Image Targets Compiler, инструмент в официальном репо): загружается изображение → извлекаются feature-точки → скачивается файл `targets.mind`. Компиляция полностью локальная, облака нет.
- Видео подключается как обычный HTML `<video>` / `<a-video>`-элемент поверх `mindar-image-target`; запуск/пауза по событиям `targetFound` / `targetLost`. Для iOS автовоспроизведение надёжнее в WebM и с `muted`/`playsInline`.
- Self-host: да, полностью — достаточно статически раздать `.mind`-файл и JS библиотеку (`mind-ar` через npm/CDN можно так же хостить у себя). Никаких серверных вызовов.
- Облачная зависимость: **отсутствует**.
- Состояние на 09.2026: v1.2.5 (январь 2024) — последний релиз; репозиторий поддерживается, но фактически одиночным мейнтейнером; активной контрибьюторской разработки мало. Это основной риск технологии.
- Ограничения: качество/стабильность tracking ниже коммерческих движков; скорость распознавания может быть заметной (особенно на средних Android); работает через TensorFlow.js WebGL; требуется перекомпиляция `.mind` при изменении изображения.

### 1.3. 8th Wall (теперь «8th Wall Open Source», Niantic Spatial)

- **Крупное событие 2026 года:** платный хостинг-платформа 8th Wall **закрыта 28.02.2026**; технология переведена в open source (`8thwall.org`, GitHub `8thwall/8thwall`). Hosted-контент удаляется до 28.02.2027.
- Две формы:
  1. **Открытый фреймворк, MIT** (`packages/engine`) — ядро, Face Effects, **Image Targets**, Sky Effects. **SLAM не включён.**
  2. **Distributed Engine Binary** (npm `@8thwall/engine-binary`, январь 2026) — включая SLAM, закрытый бинарник по ограниченной лицензии (XR Engine License Agreement), свободен для коммерческого и некоммерческого использования.
- **Image Targets** поддерживаются в обеих формах: плоские, цилиндрические и конические target'ы, до 32 одновременно.
- Image target создаётся **локально CLI**: `npx @8thwall/image-target-cli` (аналог бывшего Studio) — генерирует метаданные-файлы, которые кладутся в проект. Облака нет.
- Видео: подключается как HTML5-видео/видео-текстура к target-сущности (стандартные примеры 8th Wall). Работает в мобильном браузере, включая iOS Safari — движок месяцами позиционировался именно как «WebAR на iPhone из ссылки, без приложения».
- Self-host: **да**. Проекты деплоятся «где угодно», appKey больше не нужен (замена на self-hosted key/конфигурацию).
- Коммерческое использование: разрешено для обеих форм; attribution — сохранить уведомление «Copyright © 2026 Niantic Spatial, Inc.» и ссылку на LICENSE (в веб-коде — комментарий в заголовке `xr.js`; в упакованных приложениях — экран «О проекте»).
- Облачная зависимость: **отсутствует** (нет сервера, нет аналитики платформы).
- Состояние на 09.2026: проект в переходной стадии — репозиторий новый (февраль 2026), сообщество формируется; часть инструментов (Desktop App, ECS-компоненты, MCP) обещана следом; VPS, Maps, Hand Tracking в open source **не входят**.
- Ограничения: бинарник SLAM — закрытый (нельзя модифицировать/перекомпилировать); для нашего сценария SLAM не нужен, достаточно MIT-версии с Image Targets; экосистема молодая; Time-to-production всё ещё требует ручной сборки страницы.

### 1.4. WebXR (W3C стандарт, базовый слой + Image Tracking)

- `WebXR Device API` — зрелый стандарт (Candidate Recommendation, июнь 2026) и работает на Android Chrome (`immersive-ar` через ARCore), Meta Quest Browser, visionOS Safari (частично: `immersive-vr` есть, `immersive-ar` нет).
- **Image Tracking в WebXR** — отдельный модуль «WebXR Marker Tracking» (репозиторий `immersive-web/image-tracking`): `XRTrackedImageInit`, `getImageTrackingResults()`, `widthInMeters` — статус **Draft/explainer**, API может меняться.
- Браузерная поддержка Image Tracking-модуля (09.2026):
  - Android Chrome — реализован, но **только с флагом `chrome://flags/#webxr-incubations`** (для конечного пользователя не включён по умолчанию) → для прод-сценария «навёл камеру и всё заработало» непригоден;
  - iOS Safari / iPadOS / macOS — веб-локали **нет вообще**; AR на iPhone у Apple идёт через **AR Quick Look** (USDZ-модель в нативном AR-просмотрщике): это просмотрщик мирового размещения моделей, а не система распознавания печатных изображений с видео-оверлеем → для сценария «фото → видео» не подходит;
  - альтернатива для iOS — **App Clip мост** (например, Needle Go / Variant Launch): WebXR-код запускается внутри App Clip с ARKit. Но это уже сторонний сервис/внешний мост (см. ограничения Zappar/Needle), не «чистый стандарт из коробки».
- Лицензирование: открытый стандарт, без роялти; self-host в смысле «своего софта» не требуется — API встроен.
- Вывод: WebXR полезен как **перспективный фундамент и фоллбэк-слой**, но как основная рабочая технология для мобильного Image Tracking в сентябре 2026 не готов (пробел iOS + флаг на Android). Часть движков (MindAR, 8th Wall) уже сейчас сами используют WebGL/WebRTC — на WebXR не опираются, и это плюс.

### 1.5. ZapWorks / Zappar (Universal AR) — коммерческий вариант

- Image Tracking: да (собственное CV Zappar; есть также face/world tracking). Изображение-таргет загружается в Zapworks Designer/Studio или в пайплайн Universal AR; генерируется трекинг-ассет (оптимизация при загрузке, есть лимиты на число таргетов на проект).
- Работает в мобильном браузере через WebAR (аналог WebAR-экрана Zappar). Но: при инициализации библиотеки выполняется **лицензионная проверка** — работает только с активным workspace (и кол-во просмотров/CPV начисляется).
- Видео: привязывается к таргету в рамках проекта (Mattercraft/Designer/Universal AR SDK, видео как текстура/элемент).
- Self-host: **только Enterprise-план** (custom-цена), на один домен; даже self-hosted требует регистрации домена у Zapworks и лицензионной проверки через их сервер.
- Тарифы (09.2026): Developer — бесплатно, но **только некоммерчески** + Zappar-брендинг + `.zappar.io` хостинг + 5 target-изображений/проект + 25MB; Pro — £250/мес (12k просмотров/год, 10 target-изображений, без брендинга); перерасход просмотров — $30/1000; Enterprise — custom (white-label, self-host 1 домен, 100k просмотров/год).
- Облачная зависимость: **высокая** (хостинг Zappar на AWS, лицензионный сервер даже для self-host, CPV-учёт, «US hosting only»).
- Состояние: продукт жив, развивается; модель «плати за просмотры» для массового/долгого использования дороже open-source вариантов.
- Вывод: для постоянного публичного сервиса с долгоживущими AR-ссылками невыгоден (per-view/branding, лимит таргетов, лицензия на self-host только Enterprise).

### 1.6. AR.js (дополнительно, как открытая альтернатива)

- MIT, полностью open source; Image Tracking (NFT) + Marker + Location-based. Работает «на любом телефоне с WebGL и WebRTC», включая iOS Safari.
- Таргет создаётся **NFT Marker Creator** (веб-версия или node.js), генерирует дескрипторы (`*.fset`, `*.iset`, …) — офлайн, локально.
- Видео — обычный `<a-video>`/трёхмерный элемент поверх `a-nft`-таргета; требуются smoothing-параметры для стабилизации.
- Self-host: да, полностью (внимание к CORS — дескрипторы и контент должны отдаваться с того же домена).
- Состояние: поддержку ведут волонтеры, релизы редкие (3.4.8); рекомендуемая версия 3.4.7; архитектура старше MindAR.
- Ограничения: исторически слабее iOS-стабильность, чем у коммерческих решений; нужен ручной smoothing; консервативная (A-Frame/three.js) обвязка.

## 2. Ограничения

1. **iOS = главный ограничитель любого «чистого» подхода**: WebXR нет; Image Tracking-модуль WebXR в iOS отсутствует в принципе. Поэтому на iOS остаётся либо (а) движок с собственным CV (MindAR / 8th Wall / AR.js), либо (б) внешний мост через App Clip (сторонняя зависимость), либо (в) AR Quick Look, который наш сценарий (видео поверх распознанного фото) не покрывает.
2. **Android Chrome Image Tracking (WebXR) — только за флагом**: для конечного пользователя недоступен без ручных настроек; как прод-путь не годится на 09.2026.
3. **Автовоспроизведение видео с звуком на iOS** ограничено политикой браузеров (нужен жест пользователя либо беззвучное/`muted` воспроизведение). UX «навёл → сразу видео со звуком» на iPhone из коробки невозможен без первого тапа.
4. **Качество печатного маркера** критично: глянец (блики), низкий контраст, повторяющиеся области, мелкая детализация «шумных» фото снижают распознавание у всех движков. Требования задаются на этапе прототипов (D1.2–D1.3).
5. **Производительность на средних Android**: алгоритмы на WebGL (MindAR через tf.js, 8th Wall через WASM) чувствительны к CPU/GPU; нужна проверка «улица-освещение-бюджет-батарея».
6. **Встроенные вебвью соцсетей** ограничивают/блокируют камеру; нужен экран «откройте в браузере», а не фоллбэк-обёрток.
7. **Open-source-поддержка**: MindAR и AR.js тянутся малым числом мейнтейнеров; 8th Wall — новый open-source проект с формирующимся комьюнити; Zappar закрыт и дорог. «Бесплатность» open-source вариантов означает отсутствие гарантий и слабую обратную связь по багам в сравнении с коммерческими.
8. **Видео и мобильный трафик**: размер/битрейт/длительность напрямую влияют на время до первой картинки; без CDN/адаптивного стриминга (D1.7) тяжёлые ролики будут долго грузиться на мобильном трафике.

## 3. Вопросы, решаемые только практическим прототипом (для D1.2–D1.3)

1. **Стабильность recognition на реальной печати** (Матовые vs глянцевые, разные тиражные цвета): какой движок и при каких условиях держит target (критерий D1.2: ≥50% попыток ≥ несколько секунд).
2. **Задержка распознавания** на реальных устройствах: средний Android vs iPhone (iOS Safari).
3. **Совмещение видео с фотографией**: идеально ли позиционируется видео-оверлей, как интерпретировать «поверх фото» — 1:1 замещение фото или масштабирование; поведение при потере трекинга (пауза/стоп/восстановление).
4. **Автостарт видео (UX без установки)**: тайминги permission-запросов, повторный запрос разрешения, поведение при повторных заходах; приемлемость `muted`-старта на iOS.
5. **Пороги качества печати**: минимальные размер/контраст/разрешение печатного изображения для каждой пары «технология × телефон». (Критерий D1.3: минимум одна пара при искусственном и дневном свете.)
6. **Множественные таргеты в будущем**: сколько одновременно отслеживаемых фотографий выдерживают MindAR / 8th Wall (у 8th Wall заявлено до 32, у MindAR/AR.js надо мерить).
7. **Аппаратные пределы видео**: приемлемые битрейт/длительность/размер, скорость запуска через нашу доставку (важно для D1.7, но базовые цифры собирать на прототипе D1.3).
8. **Инструменты генерации таргетов в нашем объёме**: удобство массовой подготовки `.mind` (MindAR), NFT-дескрипторов (AR.js), метаданных CLI (8th Wall) для десятков–сотен фотографий.
9. **Стабильность токена/ссылки и «холодный старт»**: корректнее проверять уже на D1.6, но на прототипах стоит зафиксировать, что сама WebAR-страница открывается без серверной логики (чистый статик) — это подтверждает независимость AR-ссылки.

## 4. Предварительный shortlist для D1.2–D1.3

> **ВНИМАНИЕ:** это предварительный список кандидатов на прототипирование, а НЕ выбор технологии. Окончательное решение — на контрольной точке D1.5 по итогам прототипов.

1. **MindAR** (MIT) — самый зрелый активный открытый SDK именно под image-to-video;
2. **8th Wall Open Source** (MIT-фреймворк + Image Targets) — бывший коммерческий лидер WebAR, теперь бесплатен и self-host, имеет локальный CLI генерации таргетов;
3. **AR.js** (MIT) — запасная открытая альтернатива, особенно если MindAR/8th Wall на iOS покажут слабые результаты (или как B-план для фоллбэка).

WebXR и ZapWorks включаются в прототипирование как **контрольные**, но не как основные кандидаты: WebXR — из-за флага на Android и отсутствия iOS-поддержки; ZapWorks — из-за лицензионной модели (per-view) и невозможности свободного self-host.
